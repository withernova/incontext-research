# ADR-0003: Human-authorized Herdr agent execution

- Status: Proposed
- Date: 2026-08-16
- Scope: execution of approved Herdr Launch Requests

## Context

Survey Tool can discover Herdr capabilities and persist a human-governed Launch Request. Approval currently and deliberately returns `execution_started: false`. The next layer must be able to start Codex through Herdr without turning an HTTP request, an Automation transition, or a stale database row into implicit process execution.

The execution layer must also preserve these boundaries:

- approval is not execution authorization;
- execution authorization is single-use and revision-bound;
- the Web server does not control terminals or agents;
- only resources created by Survey Tool may be monitored or released;
- existing user panes and agents are never adopted;
- public APIs never expose workspace, tab, pane, terminal, session, cwd, environment, Prompt, or transcript data;
- a process exit is not a validated research result;
- Question and Experiment authority remains Markdown / legacy JSON.

## Decision

Use a three-stage contract:

```text
Launch Request approved
-> Execution Authorization authorized
-> one-shot Herdr Executor claims authorization
-> preflight
-> create owned pane and Codex agent
-> submit bounded task envelope
-> monitor and reconcile
-> completed | failed | attention_required
```

The Web API may create or revoke an authorization record, but it never invokes `herdr`. A separate one-shot executor must run from a Herdr-managed pane with `HERDR_ENV=1`.

## State model

Launch Request remains immutable after `approved` except for archival metadata. Runtime state belongs to a separate execution object.

```text
prepared
-> authorized
-> claimed
-> starting
-> running
-> completed

prepared | authorized -> revoked
claimed | starting | running -> failed
claimed | starting | running -> attention_required
claimed -> authorized       (only after an expired lease and zero owned resource)
```

`completed` means the bounded Agent turn settled and an execution summary was recorded. It does not mean a Claim is validated, a Markdown draft is accepted, an Automation is complete, or a Run is scientifically complete.

## Separate authorization gate

Execution requires all of the following in one transaction:

- Launch Request status is `approved`;
- request revision and content hash match the approved snapshot;
- target object still exists and is not archived;
- no non-terminal execution already exists for the request;
- Herdr capability preflight reports managed, CLI available, and Codex supported;
- the user submits the exact phrase `AUTHORIZE HERDR EXECUTION <request-id>`;
- authorization has a short `not_after` deadline.

Creating authorization returns `execution_started: false`. It does not create or return any execution token. The one-shot Executor generates a random lease token only during its atomic local claim; the raw token stays in that Executor process and SQLite stores only its hash. The API must not return a lease token, internal agent name, or any Herdr identifier.

## Executor model

The first implementation is an explicit one-shot command, not a daemon:

```text
python3 -m survey_tool.v2.herdr_executor --project <project> --execution <id> --once
```

The executor:

1. refuses to run unless `HERDR_ENV=1`;
2. claims one authorization using a random lease token;
3. rechecks deadline, request revision, capability, target lifecycle, and concurrency budget;
4. creates one sibling pane without stealing focus;
5. starts one Codex agent with a generated Survey Tool ownership name;
6. submits a bounded task envelope through `herdr agent prompt --wait`;
7. records only safe lifecycle summaries and irreversible identity fingerprints;
8. finishes, fails, or raises attention; then exits.

There is no polling loop in the first execution slice. A later supervised worker may be considered only after one-shot recovery has been exercised.

## Ownership and resource safety

Survey Tool must never close or send input to an arbitrary pane. Ownership is established by all of:

- the cryptographically random lease token generated by the claiming Executor;
- an internal agent name derived from the execution ID plus lease-token hash;
- an event proving the create/start response was observed by the claiming executor;
- exact matching of the live agent name during reconciliation;
- the active execution lease belonging to the same executor instance.

The project database may store the internal owned-agent name and an irreversible session fingerprint in a private execution table. Public serializers omit both. Raw pane IDs, terminal IDs, session IDs, and session paths are not persisted. Recovery discovers the owned Agent by exact internal name. If ownership cannot be proven, the executor records `attention_required` and does not send keys, stop the Agent, or close the pane.

The executor creates a sibling pane in its current Herdr workspace/tab, preserves the approved project root as cwd, and uses `--no-focus`. It does not create or close a workspace or tab in the first implementation.

## Task envelope

The Launch Request summary is not a complete Prompt. The executor builds a fixed, versioned task envelope from allowlisted data:

- target type and stable object ID;
- short approved task summary;
- task type;
- reasoning effort and maximum turns;
- project-local safety rules;
- explicit prohibition on authority changes and high-risk actions;
- a required concise final status.

No arbitrary command, cwd, environment map, credential, external project path, or hidden conversation is accepted from the browser. The full rendered envelope may be written only to a project-local private execution artifact with restrictive permissions; it is never returned by public API or copied into events. Initial implementation should avoid persisting it unless required for audit.

## Lease and concurrency

Execution claims use the existing lease principles but a dedicated table and state machine:

- claim is atomic;
- lease token is random and never returned by Web API;
- only a matching token may heartbeat or finish;
- default lease is 60 seconds, bounded to 15-300 seconds;
- only one non-terminal execution per Launch Request;
- project default Herdr execution concurrency is 1;
- concurrency resets to 1 on executor startup unless a separately approved project setting exists.

An expired lease is not enough to retry. Reconciliation first checks whether an exactly owned Agent is still live:

- no owned Agent: return to `authorized` if authorization remains valid;
- owned Agent live: `attention_required`; do not start a duplicate;
- ownership ambiguous: `attention_required` and stop.

## Completion and failure

Safe result fields are limited to:

- final execution status;
- started / settled / finished timestamps;
- bounded duration and turn count if observable;
- safe error class and cropped error summary;
- irreversible Agent/session fingerprint;
- whether a draft artifact was proposed;
- whether human review is required.

Terminal output, Codex transcript, full final response, Prompt, environment, and Herdr identifiers do not enter events or public API.

A future Draft Artifact flow may accept a project-local file produced by the Agent. That artifact remains untrusted until path confinement, size, hash, syntax, citation, target revision, and human diff review all pass.

## Cancellation semantics

- `prepared` or `authorized` execution may be revoked through a revision-bound human action.
- `claimed` but not started may be released only by the lease owner.
- `starting` or `running` is not force-cancelled from the Web UI.
- an explicit emergency stop may be added later, but only with ownership attestation and a second exact confirmation phrase.
- no Web action closes a pane in the first implementation.

## API boundary

Planned public endpoints:

```text
GET  /api/v2/p/<project>/herdr-executions
POST /api/v2/p/<project>/herdr-launch-requests/<id>/authorize
POST /api/v2/p/<project>/herdr-executions/<id>/revoke
```

They manage records only. Every response includes `execution_started: false` unless it is a read of an execution already observed as running by the external executor. No endpoint accepts a pane ID, session ID, command, Prompt, cwd, environment, or executable path.

Executor-only repository methods are not exposed as browser endpoints. A later local IPC boundary must authenticate the executor before any claim/heartbeat/finish API is considered.

## Recovery rules

On process or service restart:

1. read non-terminal executions;
2. do not infer running from database state alone;
3. use read-only Herdr discovery to find an exact owned-agent name;
4. reconcile only when ownership proof is complete;
5. never adopt neighboring Codex or pi agents;
6. preserve ambiguous cases for manual review.

## Implementation slices

1. **Execution records only**: schema, authorization/revoke state, revision, deadline, event, privacy-safe serializers; no Herdr invocation.
2. **Read-only executor preflight**: one-shot CLI verifies Herdr environment/capability and records a dry-run report; no pane creation.
3. **Owned Agent start**: create sibling pane, start named Codex, record ownership attestation; no task prompt yet.
4. **Bounded prompt turn**: fixed task envelope, `agent prompt --wait`, hard timeout, safe completion summary.
5. **Reconciliation**: lease expiry and exact-name ownership recovery; no force-close.
6. **UI operations**: authorization deadline, revoke, runtime status, attention state, and audit timeline.
7. **Draft Artifact handoff**: separately reviewed design for Agent output and canonical Markdown writes.

Each slice must use mocked Herdr responses in automated tests. A real Herdr smoke test must use a disposable Agent/pane created for that test and require explicit human initiation.

## Rejected alternatives

### Invoke Herdr directly from the HTTP request

Rejected because retries, browser requests, CSRF, and server lifecycle would become process-control authority.

### Treat Launch Request approval as execution authorization

Rejected because review approval and resource execution are different human decisions.

### Persist pane and session IDs in public project state

Rejected because these identifiers leak terminal topology and make accidental adoption easier.

### Automatically reuse any idle Codex pane

Rejected because idle does not prove Survey Tool ownership and could overwrite unrelated user work.

### Start with a permanent polling daemon

Rejected until one-shot execution, ownership attestation, and restart reconciliation are proven.

## Consequences

This design adds an extra human action and an explicit executor command. That is intentional. It makes process creation auditable, keeps HTTP away from terminal control, and prevents Survey Tool from taking ownership of existing Herdr work. It also postpones convenient automatic execution until recovery and ownership behavior are demonstrated under real failures.
